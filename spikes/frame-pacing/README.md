# frame-pacing — 120Hz 박자 실험

새 카사라이트 렌더러가 프레임을 어떤 방식으로 낼지 고르려고 잰 실험이다(kasaterm `docs/terminal-engine.md` §4.2 A/B).
앱 워크스페이스 밖의 독립 크레이트다.

```bash
cd spikes/frame-pacing && cargo build --release -j 4
target/release/frame-pacing --mode link-imm --latency 2 --hold-ms 0     # 한 줄 JSON 보고를 stdout 으로
```

한 번에 약 15초, 200×60 칸 격자를 그리며 구간을 돈다:
데우기 → **폭주**(매 프레임 칸 전부 바꿈, 3초) → 쉼 → **키 30개**(150ms 간격, NSEvent keyDown 을 winit 뷰에 직접)
→ 쉼 → **다시 폭주**(쉼 뒤 첫 프레임들이 곧바로 120Hz 로 뜨는지).

- 화면에 실제로 뜬 시각은 Metal `presentedTime` 으로 받는다. wgpu 가 drawable 을 내놓지 않아
  `-[CAMetalLayer nextDrawable]` 을 프로세스 안에서 감싸 drawable 마다 presented 손잡이를 단다(`mac.rs`).
  화면 녹화 권한 없이 박자를 잴 수 있는 길이다.
- `KASALITE_TRACE=<경로>` 면 `bench/README.md` 형식으로 기록을 남긴다. `bench/measure.py` 의 계약 표본이다.

| `--mode` | 박자 | present |
|---|---|---|
| `timer` | 8ms `WaitUntil` 펌프(옛 본판 방식) | AutoNoVsync |
| `fifo` | 쉬지 않고 그림, `get_current_texture` 가 박자에 막힘 | Fifo |
| `link-fifo` | 디스플레이 링크(`NSView.displayLink`, 선호 120·최소 80) | Fifo |
| `link-imm` | 디스플레이 링크 | Immediate |

`--latency` 는 `desired_maximum_frame_latency`(drawable 수 = 값 + 1), `--hold-ms` 는 키 뒤 링크로 같은 화면을 계속
내는 시간(ProMotion 이 주사율을 내리지 않게 붙잡기)이다.

## 결과 (2026-10-06, M3 Max 내장 120Hz, macOS 26.5)

다른 칸의 `rustc`·시뮬레이터·창 서버가 함께 도는 맥에서 쟀다(앱 메모리 부족 재시작이 두 번 났던 날). **같은 설정이
판마다 50~120fps 를 오갔다** — 박자 방식보다 기계 부하가 더 크게 흔든다. 그래서 판마다 값이 아니라 중앙값으로 본다.
조용할 때 한 판씩은 `fifo`(119fps, 간격 p99 8.3ms)와 `link-imm` 대기열 2(118fps)가 120Hz 에 붙었다.

| 설정 | 판 | 폭주 fps 중앙(범위) | 간격 p99 | drawable 대기 p50 | 키→present p50 | 키→화면 p50 / p95 | 쉼 뒤 폭주 fps |
|---|---|---|---|---|---|---|---|
| `timer` 대기열 1(옛 본판) | 7 | 73 (51–109) | 50.0 | 0.0 | 0.3 | 8.6 / 19.0 | 71 |
| `timer` 대기열 2(지금 본판, 90666980) | 6 | 87 (38–94) | 43.6 | 0.0 | 0.3 | 12.6 / 21.1 | 92 |
| `fifo` 대기열 2 | 7 | 85 (60–119) | 46.7 | **8.1** | 0.3 | 9.7 / 19.0 | 70 |
| `link-fifo` 대기열 2 | 5 | 67 (2–110) | 69.3 | **7.2** | 0.3 | 12.2 / 24.9 | 67 |
| `link-fifo` 대기열 2·붙잡기 1초·미룸 | 3 | 94 (92–98) | 20.0 | 8.4 | **9.5** | **39.9 / 49.4** | 93 |
| `link-imm` 대기열 1 | 2 | 91 (67–114) | 65.4 | 0.0 | 0.3 | 9.1 / **85.7** | 80 |
| `link-imm` 대기열 2 | 9 | 96 (70–118) | 25.9 | 0.0 | 0.3 | 15.8 / 24.2 | 98 |
| `link-imm` 대기열 2·붙잡기 1초 | 4 | 67 (59–87) | 63.4 | 0.0 | 0.3 | 11.6 / 33.8 | 63 |
| `link-imm` 대기열 2·붙잡기 1초·미룸 | 3 | **106 (94–109)** | 24.9 | 0.0 | 2.1 | 16.6 / 25.5 | **101** |

단위는 ms(fps 빼고). 「키→화면」은 키 이벤트를 받은 때부터 그 프레임의 `presentedTime` 까지다.

알아낸 것:

- **대기열 1(drawable 2장)은 GUI 스레드를 세운다.** `link-imm` 대기열 1 에서 `nextDrawable` 안 대기가 p50 7.2ms·
  최대 82ms 였고, 키→화면 p95 가 86ms 로 튀었다. 대기열 2 면 p50 0.06ms. 본판도 같은 이유로 90666980 에서 3장으로 갔다.
- **Fifo(디스플레이 동기)는 박자를 `get_current_texture` 에서 막아서 맞춘다.** 프레임마다 8ms 를 GUI 스레드에서 쉰다 —
  그 사이 온 키·PTY 출력은 다음 박자까지 못 그린다. 링크로 박자를 주고 Fifo 로 내면 키가 링크 대기와 Fifo 대기를 둘 다 타서
  키→화면이 40ms 까지 늘었다.
- **ProMotion 은 쉰 뒤 주사율을 내린다.** `link-imm` 붙잡기 없이 쉬었다 다시 그리면 첫 프레임 간격이 16.7ms(60Hz)로 시작하는
  판이 있었다. 키 뒤 1초 붙잡기는 폭주 fps 를 올렸지만, 키를 바로 그리면 붙잡기 박자와 drawable 을 다퉈 오히려 나빠졌다.
  붙잡는 동안은 키를 다음 박자에 싣는 「미룸」이어야 이득이 남는다.
- **키→present 는 0.3ms 로 이미 목표(≤3ms) 안이다.** 키→화면 10~16ms 의 대부분은 창 서버 합성과 주사 대기다. 앱이 줄일 수
  있는 몫은 「키를 바로 그린다」와 「그때 화면이 120Hz 로 돌고 있다」 둘뿐이다. Typometer 기준 평균 ≤8ms(§4.3)는 macOS 창 모드
  합성을 거치면 닿기 어렵다 — L2 에서 실물로 다시 재고, 안 되면 목표를 고쳐 적는다.
- 쉬는 동안 깨어남은 모든 방식이 2.5초에 1~2번(구간 경계 타이머)이다. 링크는 멈춰 두면 박자를 안 보낸다.

## 고른 것

새 카사라이트 렌더러(L2)는 이렇게 낸다.

- **macOS**: `NSView.displayLinkWithTarget:selector:`(선호 120·최소 80) + **Immediate**(`setDisplaySyncEnabled:NO`) +
  **drawable 3장**(`desired_maximum_frame_latency: 2`). 출력·애니메이션은 링크 박자에 그리고, 할 일이 없으면 링크를 멈춘다.
- **키는 바로 그린다.** 다만 입력·출력 뒤 1초 동안 링크로 화면을 붙잡는 중이면 키를 다음 박자에 싣는다(미룸, ≤8.3ms 대기).
- **Windows**: 링크가 없으니 모니터 주사율(`refresh_rate_millihertz`)에 맞춘 `WaitUntil` 박자 + DX12 flip,
  대기열 2. 키는 바로 그린다.
- 같은 화면을 다시 낼 때 오프스크린 결과만 복사하는 것(§4.2)은 붙잡기 비용이 문제 될 때 더한다 — 이 실험의 격자 그리기는
  0.3ms 라 아직 필요가 안 보였다.
